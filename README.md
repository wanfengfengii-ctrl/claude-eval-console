# Claude Eval Console

本地可视化工具，用于从空 GitHub 仓库开始运行容器化开发任务，完成逐轮检查、Bug 修复和交付整理。

## 功能

- 点击“新建任务”后，按四位项目编号生成唯一仓库名、单段第一轮 Prompt 和验收命令，复核通过后自动打开 Mac 终端；编号只写入 `0001-项目名` 形式的文件夹名称，不进入题面正文
- 每条任务新建独立的本地目录、`screen` 终端会话和 Docker 容器，容器内工作目录固定为 `/workspace`
- 0-1 任务会在 `makabaka-boop` 下创建公开仓库，首个提交只包含空 `README.md`
- 每 10 个编号包含 4 个纯后端、3 个纯前端和 3 个全栈项目，所有题目均要求使用 Docker Compose 运行与验收
- 出题先生成 1 个完整候选并执行本地硬校验和独立复核；只有候选无法通过或无法定向修复时才按需生成下一候选，避免正常路径为未使用的备选题支付输出成本。历史重复会直接换候选，范围、难度或边界问题最多定向改写一次，改写时携带稳定的失败类型和完整复核结论。独立复核还会保存一份内部难度契约，固定一个主难点轴、不可删除的困难要求、直接验收证据和无法通过验收的简化捷径；若最简合规实现仍能绕开困难机制，候选不会开工。整段出题流程最多运行 10 分钟；任务失败后保留原编号和失败原因自动重试一次，用户取消不计入自动补题失败。历史题先压缩为摘要，生成阶段最多携带 15 条，复核阶段只比较最相近的 10 条。0-1 题面目标约 450 字，生成提示要求 300 至 520 字，本地硬校验接受 300 至 600 字；题目必须有且只有一个可独立验收的工程核心和一条主要纵向链路，范围限于 3～4 个实现模块、最多 2 个应用运行组件、最多 2 项核心外辅助机制、全题最多 1 项复杂状态机制、最多 1 种自定义算法体系以及 3～6 个验收场景，其中复杂状态机制与自定义算法不能同时出现。同一次操作下只产生同一个最终结果的多项检查合并为一个验收场景。会导致核心验收结果不唯一的规则、机制堆叠和无职责基础设施属于硬错误；开头、结尾、通用交付项位置及次要实现选择只参与择优或作为复核建议，不单独阻断。任务创建时不预设最终难度，最终难度仍由开发轨迹和产物决定；完成后若实际只达到简单或中等，该轮保留且不提交，系统优先沿用现有仓库生成一条不同扩展轴的 Feature 迭代，即使普通自动补题开关关闭也不会废弃已有代码。题目不能以普通 CRUD、审批、档案、认领、留痕或泛化“XX 管理系统”为主体，也不叠加分布式架构、复杂求解器、完整编译器、重型调度或多套高并发机制
- 已创建的首轮题面会自动追加到 `history-prompts.md`；即使 SQLite 记录迁移，后续出题仍会读取这份文档参与查重
- 保存初始 commit permalink
- 可在页面统一切换 Claude Code 模型，新容器启动时会把选中值传入容器
- 最多同时运行 6 个项目，超出的任务自动排队
- 终止只作用于当前记录的容器和终端，不处理其他 Claude 会话
- 每轮 Claude 交付后先运行验收，再创建并推送独立 Git 检查点；提交正文固定写入 `Session-ID`、`Turn-Number` 和 `Turn-ID`（即 PromptID），随后持久化 `projects/-workspace/<SessionID>.jsonl` 原始完整轨迹快照，并另外导出截至该轮完成边界的逐轮轨迹，全部成功后才使用 `gpt-5.6-sol` 找 Bug。Docker Compose 验收按运行记录使用独立项目名和动态宿主端口，结束后只清理该项目，避免不同任务互相复用容器或抢占端口。普通验收命令默认最多运行 15 分钟；显式 `docker compose build` 默认允许 90 分钟冷构建，并在没有手工指定 profile 时预先构建所有 profile 服务，继续复用 BuildKit 层缓存。若构建仍失败或超时，依赖镜像的后续 `docker compose run`/`up` 会明确标为 `SKIPPED`，不再隐式重复构建
- 运行期间的日常监控只读取容器状态、轨迹内容增长和终端当前画面，不发送心跳、测试消息，也不会代替用户确认业务执行；发现操作确认、按键确认或补充指令提示时，列表立即显示“等待人工确认”，macOS 宿主机每 60 秒播放一次系统提示音，提示消失后继续普通监控。响铃和状态更新都发生在控制台侧，不产生新的 User Prompt、TurnID 或轨迹事件。终端粘贴给题面增加少量首尾空白时仍能识别同一 PromptID 和完成回复；单纯刷新轨迹文件修改时间不算新活动。累计运行超过 6 小时且连续 30 分钟没有真实轨迹增长时，系统自动导出轨迹、保留工作区代码并关闭容器，避免完成信号丢失的会话长期占用并行槽
- 容器在交付前退出时自动保留本地代码、导出轨迹并标记为中断，可从原始快照创建全新容器和 SessionID 重跑
- 任一 Claude 开发轮遇到 408、429、500、502、503、504 等临时 API 错误，或 CLI 在网络重试后结束但没有生成最终回复时，先保留容器并在原 Session 自动输入一次“继续”；恢复后沿用已有上下文、代码和轨迹完成当前轮。发送后等待 30 秒仍未恢复，或同一轮再次出现临时中断，才归档现场并从该任务初始快照使用新会话重跑，最多 2 次；只按 `retries/retry-01`、`retry-02` 计算新会话重跑次数，原会话的“继续”不占次数，0-1 与 Feature 的项目迭代层级也不占用次数。重跑目录归入原编号的 `retries/retry-XX`，不占用下一道题编号；用户主动中断以及 401、403 等鉴权或权限错误不会自动输入“继续”，只提示人工处理
- Claude 输出本轮最终回复后，控制台立即把该轮标记为“完成/会话空闲”，交互容器继续存活；Git 推送、轨迹检查点或复核遇到临时网络故障时按退避时间自动重试两次，仍失败时保留现场并提供“重试当前阶段”，不会发送下一轮题面。上游接口临时中断后自动发送的“继续”属于同一逻辑轮次，轨迹检查点会保留中断前后的完整事件和恢复后的最终回复；轨迹尚未落盘也会自动重试，不再直接判定运行失败。复核过程误把控制台验收命令写进五维描述时，系统会自动改成不冒充开发过程的验收表述；旧版本因此中断且已形成 Git 检查点的任务会在重启后重新进入原复核阶段，不会让远端新提交失去可用基线
- 找 Bug 从该轮已推送 commit 创建一次性隔离工作区，允许执行复现命令但不回写 Claude 工作目录；必须给出稳定复现步骤、实际结果、预期结果以及文件或函数、命令、响应、日志或数据库状态证据。独立复核优先核对这份证据，只在证据缺失、矛盾或无法对应当前提交时补跑同一检查；未复现风险、缺少测试、覆盖不足、文档不足和代码结构问题只记为质量建议，不触发 Bug 修复轮
- Bug 复核与五维评分分成两个阶段：复现结论先同时写入任务和轮次记录，再并行独立评定交付完整性、指令遵循、任务规划、推理能力和执行能力。每维保存 `when`、`behavior`、`impact`、`expected`、`evidenceRefs` 与相邻档依据；评分遇到 504、服务重启或单分片失败时保留 Bug 结论，恢复后只重试评分，不重复找 Bug
- 确认真实 Bug 后，修复题面始终发送给同一个容器、终端和 SessionID，并产生新的 TurnID；完成后再次按“验收 → Git 提交并推送 → 轮次轨迹导出 → 复查”执行，直到没有真实 Bug 或达到 10 轮上限
- 没有确凿 Bug 时导出完整会话轨迹，再关闭 Claude 会话并删除本题容器；各轮检查点已经提前推送和导出，不在最终检查阶段重复提交
- 后续迭代必须从已通过检查的 commit 快照新建任务，使用新目录、新容器、新终端和新 SessionID，不续接 0-1 对话；目录沿用源项目主编号并追加迭代序号（如 `0003-1-项目名`、`0003-2-项目名`），不占用下一道 0-1 新项目的四位主编号
- 每一轮都单独保存 User Prompt、PromptID、Git commit、轨迹文件、轨迹 SHA-256、模型、返回结果、Docker 验收、任务类型、难度、环境等级、五维评分和具体依据；五维评分直接读取 `doc.md`“第三步”的 1～5 分档标准，禁止换算为其他分制，分数和描述必须与本轮轨迹、产物证据一致；任务创建时难度为“待评估”，0-1、迭代和 Bug 修复均在该轮结束后由检查模型依据真实轨迹、代码产物与验收结果判定；`traces/<SessionID>/manifest.json` 记录轮次、提交和轨迹哈希的对应关系
- 切换模型后，新任务和尚未启动容器的排队任务使用新模型；已启动的容器为了保持原 SessionID 不中途切换
- 详情页按轮次展示所有 PromptID、模型、完整题面、执行结果和检查结果
- 详情页记录初始仓库、第一轮开发、首轮检查、后续轮开发和逐轮复查的累计耗时，当前环节每分钟更新；生成、独立复核、查重和局部修复的模型调用还会单独记录提示长度、重试次数、耗时与结果，便于比较优化前后速度
- 运行记录页可按编号或关键词、任务类型、项目类别和状态组合筛选；终态记录可从列表隐藏，数据库采用可恢复的软删除，本地项目与 GitHub 仓库始终保留。有后续迭代记录时须从最末端开始处理
- “导出完成轮次”页面列出所有状态为完成的轮次，每行最左侧可展开查看该轮完整题面，并逐项校验真实 SessionID、PromptID、40 位 Git commit、GitHub commit 快照、轨迹文件及 SHA-256、五维评分和数字 Harness 版本；资料不全的行会显示原因且不能勾选。合规轮次可多选生成真实 `.xlsx`，每个轮次占一行，最前面固定为“编号”和“项目 / 仓库”，随后是详情页“复制交付信息”的字段，文本会进行 Excel 公式注入防护
- 进入导出页时立即读取一次完成轮次，停留期间每 5 分钟自动更新；运行记录与环境状态仍按 3 秒刷新。任务列表和导出列表默认每页显示 20 条，表格上方、下方都能切换页码；筛选后返回第一页，自动刷新时保留仍然有效的当前页。展开轮次后的五维描述输入框默认显示 6 行并允许继续向下拉伸
- 导出页面可通过随仓库提供的 Chrome 提交助手同步 SOLO-QA“我的提交”，以 SessionID、TurnID 和轮次匹配历史记录；选择一个或多个合规轮次后，可自动读取远端最新表单结构、上传已校验摘要的轨迹、逐条提交并把质检状态和远端编号写回本地。批量操作遇到首条失败即停止，网络结果不确定时先回查远端，已提交轮次不会盲目重复创建
- 可配置每轮结束后的验收命令
- 本地 SQLite 保存任务和运行轨迹

## 启动

```bash
cd "/Users/zhangxinyu/claude code/claude-eval-console"
python3 app.py --open
```

默认地址为 <http://127.0.0.1:8765>。

## macOS 常驻启动

本机使用 LaunchAgent `com.makabaka.claude-eval-console`。它会在用户登录后自动启动，服务异常退出时自动重启，且始终只监听 `127.0.0.1:8765`。

查看状态：

```bash
launchctl print gui/$(id -u)/com.makabaka.claude-eval-console
```

手动重启：

```bash
launchctl kickstart -k gui/$(id -u)/com.makabaka.claude-eval-console
```

服务日志位于 `.data/server.stdout.log` 和 `.data/server.stderr.log`；带运行编号与阶段的工作流异常写入自动轮转的 `.data/workflow.log`（最多保留 3 个历史文件）。每条交付验收命令的完整实时输出保存在 `.data/verification/<run_id>/`，运行页面同时滚动显示最近进度；命令超时时，验收记录会保留超时前的输出尾部。

控制台自身检查：

```bash
pytest -q
node --check static/app.js
node tests/test_solo_helper.mjs
python3 -m py_compile app.py
```

启动前需要确认 Docker Desktop 已启动，并准备好本次任务的 API Key：

```bash
gh auth status
docker info
codex --version
git --version
```

## 可选配置

```bash
export CLAUDE_EVAL_GITHUB_OWNER="makabaka-boop"
export CLAUDE_EVAL_PROJECTS_ROOT="/Users/niuyuhang"
export CLAUDE_EVAL_DEFAULT_DIRECTORY="claude-eval-projects"
export CLAUDE_EVAL_MODEL="auto_model/urm"
export CLAUDE_EVAL_MODELS="auto_model/urm,model_hub/example-model"
export CLAUDE_EVAL_DOCKER_IMAGE="claude-eval-console/claude-code:2.1.269"
export CLAUDE_EVAL_MAX_PARALLEL="6"
export CLAUDE_EVAL_HARNESS_VERSION="2.1.269"
export CLAUDE_EVAL_SUBMITTER="牛宇航"
export CLAUDE_EVAL_AUTO_CLOSE_TERMINAL="1"
export SOLO_QA_MAX_TOTAL_SCORE="21"
export CLAUDE_EVAL_VERIFICATION_TIMEOUT_SECONDS="900"
export CLAUDE_EVAL_COMPOSE_BUILD_TIMEOUT_SECONDS="5400"
export CLAUDE_EVAL_ARTIFACT_NODE="/path/to/codex-primary-runtime/dependencies/node/bin/node"
export CLAUDE_EVAL_ARTIFACT_NODE_MODULES="/path/to/codex-primary-runtime/dependencies/node/node_modules"
python3 app.py
```

模型下拉框默认提供 Default、Opus 1M、Sonnet、Sonnet 1M 和 Haiku，并合并当前全局模型及 `CLAUDE_EVAL_MODELS` 中以逗号分隔的自定义模型。默认镜像已配置 `auto_model/urm`，启动脚本同时使用 `ANTHROPIC_MODEL` 传入当前选择。新任务启动时会依次尝试 `CLAUDE_EVAL_DOCKER_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_API_KEY` 和 `~/.claude/settings.json` 里的本机认证配置，只把取到的值传入本题容器，不写入页面、SQLite 或启动脚本。只有自动读取失败时，Terminal 才会要求手动输入。任务完成并成功导出轨迹、删除容器后，控制台会关闭该任务自己打开且已经空闲的 Terminal 标签页；失败、人工确认或仍忙碌的标签页会保留，设置 `CLAUDE_EVAL_AUTO_CLOSE_TERMINAL=0` 可关闭此行为。页面只监听 `127.0.0.1`。

运行记录是默认页面，列表直接展示任务开始时间和最近更新时间，并支持按当前对话轮次、开始时间和更新时间排序；语言 / 框架与模型不占用列表列位，仍可在记录详情中查看。页面还可通过编号或关键词、任务类型、项目类别和状态筛选。点击“新建任务”后会在 `0001–2999` 号段预留下一个未使用编号并立即在列表写入“题目生成中”，题面在后台生成并原地补全同一条记录；刷新页面不会丢失进度，同一生成任务未结束时重复请求只返回原记录。自动迭代尚在生成题面、还没有创建正式项目时，也会以蓝色“待创建 / 题面生成中”只读占位行出现在列表；占位行显示来源项目和当前生成阶段，点击可查看来源任务，通过校验并创建正式任务后会被真实记录自动替换。题目生成失败时，详情页会保留具体校验原因并提供“沿用原编号重新生成题面”，重试不会消耗新的顺序号。该号段中的顶层 `NNNN-*` 目录会占用普通新项目编号，`3000–3999` 导入号段不会把下一道普通题跳到 3001。点击记录进入详情后，可直接查看完整题面、技术信息和验收命令，并通过浏览器后退或页面按钮返回列表。列表删除只做软删除，不删除轮次证据、本地目录或远端仓库；运行中的记录不可删除，存在子迭代时会返回明确提示。误删可调用 `POST /api/runs/<run_id>/restore` 并发送空 JSON 对象恢复。

顶部使用“运行记录 / 导出轮次 / 数据分析”三个 Tab。数据分析页默认按上海本地日期展示 24 个自然小时的完成轮次总量、峰值时段、活跃小时、全天均值和任务类型分布，也可切换日期查看历史产出。0-1、Feature、Bug 修复和其他类型的当天总条数使用与核心指标一致的概览卡片展示。小时趋势可在柱状图与折线图之间切换；鼠标悬浮或键盘聚焦图表标记时，会显示该时段的总量和各任务类型明细。统计只计入 `status = complete` 的真实完成轮次；从导出列表软隐藏的轮次仍属于已经发生的产出，因此继续计入。

运行记录页的“导入现有 0-1 基线”用于登记在本机完成、准备继续出迭代题的项目。页面只需填写一个或多个 `3000–3999` 编号以及保存分组，例如 `3000, 3001`；控制台按编号寻找唯一的顶层项目目录，自动读取 README、项目类别、语言/框架、GitHub commit 和 Docker Compose 验收入口。导入只接受位于 `CLAUDE_EVAL_PROJECTS_ROOT` 内、README 信息足够、工作树干净、`origin` 指向 GitHub、当前 HEAD 与远端 `main` 一致且 `docker compose config --quiet` 通过的仓库。已登记编号重复提交时直接返回原记录；同批其他编号失败不会回滚已经成功的项目，页面会逐项写明缺失目录、README、Git 或 Compose 等原因。导入记录没有 Claude 会话，因此不会伪造 SessionID、PromptID、轨迹或可导出轮次；它只保存 GitHub 初始快照并作为手动迭代和自动补题的根基线，后续目录继续使用 `3000-1`、`3000-2` 等编号。

页面顶部的“自动补题”开关默认关闭，状态和保存目录写入 SQLite，控制台重启后保持不变。关闭状态下可以输入 0.5～168 小时预约开始，页面显示开始时刻和倒计时；到点后协调器自动开启补题，也可以更新预约、取消预约或提前立即开启。开启状态下可以输入 0.5～168 小时设置定时关闭；关闭时刻同样持久化，页面显示具体时间和剩余时长，到点只停止创建新任务，已经启动的开发任务继续运行。也可以更新或取消关闭定时，改为持续开启。开启后，协调器每 5 秒检查一次容量，把手动题面生成、自动出题、开发、检查和修复共同计入最多 6 个并行槽；已经确认的后续 Bug 修复沿用原任务并优先取得空槽。仍有容量时，系统优先从已完成且有效任务数不足 6 的根项目中继续出题，失败或中断且没有产物的任务不消耗额度，重跑成功只按原任务计一次；同一项目链同时只运行一个独立任务。若 SOLO-QA 将任一轮标为需要返修或废弃，且质检原因明确命中雷同题库、常见小应用或项目/题目/题面/选题/题材不合格，整条根项目链都会退出手动及自动补题选源；普通的内容返修不会误伤项目链。自动链在第 1、4 个位置生成 Feature，第 2、5 个位置生成基于现有代码的 Bug 修复题，第 3、6 个位置可以穿插完整模块构建；每条链最多两个 0-1 完整模块且不能连续出现。Bug 修复题仍须先复现三至四个范围适中的真实问题，并在内部保存 reproduction、actual、expected、evidence 和小或中的修改范围。开发者最终看到的题面只由项目专属范围说明和各问题的自然 customer_summary 组成：不添加固定开头，不套用“当……当前表现……正确结果……”句型，也不追加回归测试、Docker Compose 或范围免责尾巴；容器验收继续由控制台内部执行和保存。摘要中的编号、引号、连续标点和多余句末符号由本地程序直接整理，不再让整次候选生成失败；真实复现证据、项目关联、实现方案泄露和历史实质重复仍按硬条件检查。Bug 题面生成的单次检查最多运行 12 分钟，超时、实质字段缺失或复核异常会携带失败原因再生成一次；两次仍失败时让该来源冷却 30 分钟并继续选择其他来源。Feature 和完整模块题只因字数、句数、分号或模板化表达未通过时，只修复题面表达并重新执行本地硬校验，不再重新分析仓库；难度、范围或核心边界问题优先在同一候选上定向修复并复核，只有历史重复、类型错误、Bug 证据不足或定向修复仍失败时才生成新候选。提交前语义查重默认由本地完整历史检查和独立复核完成，只有跨仓库短名单达到相似风险阈值时才增加一次高精度模型查重；模型只接收按相关性排序后的少量历史。出题与复核遇到 429、504 或短暂网络中断时在原总时限内退避重试，不会因为重试重新获得一整段超时。单纯的长度、措辞或独立复核不通过属于候选质量问题，会清零平台故障计数，不再暂停整个队列；只有连续 3 个超时、模型调用、连接或任务执行等系统性失败才暂停全局补题，暂停后已经在途的结果不会继续增加计数或覆盖暂停原因。完整模块候选未通过时自动退回范围更小的 Feature。没有合适来源时才创建新的顶层 0-1 项目。顶层 0-1 出题每次先生成一个完整候选，独立复核不通过时只按原题定向改写一次，仍失败才按需生成下一候选；页面显示候选生成、独立复核和定向改写进度。新题面禁止出现待办清单、任务清单等常见小应用题材，也不再写出容易被题库分类器误判为待办应用的英文占位词，统一改写为“占位实现”。

完成轮次导出页支持按编号或项目、任务类型、难度、资料状态、SOLO-QA 状态和完成日期范围组合筛选；表头全选只作用于当前筛选结果，筛选前已勾选的其他轮次会保留并在计数中注明。单条“删除”和“删除所选”只把完成轮次从导出列表软隐藏，不删除运行记录、项目代码、GitHub 仓库、轨迹证据或 SOLO-QA 远端提交，可通过 `POST /api/exports/turns/restore` 携带 `turn_keys` 恢复。完成轮次导出依赖 Codex 桌面环境附带的 Node.js 与 `@oai/artifact-tool`。默认会从 `~/.cache/codex-runtimes/codex-primary-runtime/dependencies` 读取，也可使用 `CLAUDE_EVAL_ARTIFACT_NODE` 和 `CLAUDE_EVAL_ARTIFACT_NODE_MODULES` 指向兼容运行时。导出失败会返回结构化错误，不会生成空文件或 CSV 伪装的 Excel。

五维仍按交付完整性、指令遵循、任务规划、推理能力和执行能力独立并行评分；本版本新生成的评分汇总超过 `SOLO_QA_MAX_TOTAL_SCORE`（默认 21）时，系统只追加一次联合校准，依据本轮真实不足把最接近下一档的维度下调并同步重写公开描述及内部证据。任何维度都不能升分，也不能用环境故障或编造问题凑总分。材料不足以安全校准时保留原始评分并阻止导出和提交，供人工确认。更新前已经形成的旧评分不补标策略版本，也不会被追溯改分、拦截或排入自动修复队列。

独立 Bug 修复的候选通过复核后，控制台会把来源任务、来源提交、复核时间、逐项 reproduction、actual、expected、evidence、修改范围、客户摘要和独立复核结论一起保存到新任务记录；开发者仍然只看到自然题面，后续重跑继续沿用原始证据。

## 提交到 SOLO-QA

首次使用需要安装本地 Chrome 提交助手：

1. 在 Chrome 打开 `chrome://extensions` 并开启“开发者模式”。
2. 点击“加载已解压的扩展程序”。
3. 选择 `/Users/niuyuhang/.local/share/claude-eval-console/chrome-solo-qa-helper`。
4. 登录 <https://solo2.jzxhnh.com>，然后刷新 <http://127.0.0.1:8765/#exports>。

导出页显示“提交助手已连接”后不会自动遍历历史记录，页面直接使用本地保存的最近状态；需要核对质检结果或自动处理返修时，再点击“同步并自动返修”。同步只读取北京时间当天的提交并读取详情，翻页遇到更早日期后立即停止，再用 SessionID 与 TurnID/PromptID 精确匹配本地完成轮次；因为不再遍历完整历史，这个快速同步不会据此判断旧记录是否已被远端删除。当天五维点评和可见的查重摘要会以受限字段保存在本地，供后续评分避开本人历史表达。对于质检原因能由本轮题面、轨迹和验收结果安全修复的待返修项，系统会自动重写命中维度、重新执行提交前检查，并更新原 SOLO-QA 记录；缺少证据、修复失败或检查不通过的记录仍保留给人工处理。该历史只覆盖当前账号能读取的数据，不冒充 SOLO-QA 全局查重结果。正式提交只对本次所选且本地尚未提交的轮次按相同标识做精确回查，不重复核对已经质检通过的历史记录；同批轮次复用一次远端表单结构，提交成功后先记为质检中，后续状态由同步更新。

选择轮次后点击“提交所选轮次”，确认弹窗中列出的编号、仓库和轮次。助手会动态获取 SOLO-QA 当前表单 fingerprint，将本地任务类型转换成远端规范值，校验并上传不超过 20 MB 的轨迹，再按顺序提交。状态包括未提交、提交中、质检中、质检通过、需要返修、已废弃、提交失败、远端未找到和本地数据已变化。需要返修或提交后本地数据又有改动的记录不会作为新数据重复提交，应从远端详情处理。

扩展的权限只覆盖 `http://127.0.0.1:8765/*` 和 `https://solo2.jzxhnh.com/*`。它使用 Chrome 当前的 SOLO-QA 登录状态，不读取或保存账号、密码和 Cookie；只有在本地页面明确点击提交，或点击“同步并自动返修”且存在可安全修复的退回项时，才会上传轨迹并写入远端。对 `Failed to fetch`、429、502、503、504 等临时故障会自动退避重试；单条最终失败会保留错误并继续处理同批其他记录。

详情页的“复制交付信息”按轮次输出固定字段，包含 Prompt、SessionID、PromptID、纯数字轮次排序、本轮 Git commit、GitHub 初始快照、本轮轨迹文件、环境信息、任务元数据和五维评分；提交人固定为“牛宇航”。导出列表展开一条记录后会同时显示题面和五维评分，允许人工修改五项分数与描述；人工版本单独保存，原始自动评分仍保留，后续 Excel 导出、提交前检查和 SOLO-QA 提交统一优先使用人工版本，也可以一键恢复自动评分。Harness 版本从任务所用 Claude Code 镜像读取并只保存 `2.1.269` 这类纯数字版本，必要时可用 `CLAUDE_EVAL_HARNESS_VERSION` 明确指定。每个轮次卡片也展示 commit、轨迹路径和 SHA-256。评分描述只使用本轮轨迹、Git 变化和验收结果中可以核对的事实，数字、成功或失败以及修改前后状态必须与证据一致；没有发生的波折不能为了凑结构补写。五个维度分别说明交付结果、明确约束、实际步骤、判断依据和执行表现，避免复用相同开头与收尾。描述直接陈述行为和结果，不出现 AI 身份、AI 浏览器、AI Agent、Codex、GPT、Claude Code 等工具或模型名称，也不用“模型认为”“模型完成了”等执行者称谓；自动生成会立即检查，人工草稿可先保存但必须在导出和提交前通过相同核心检查。任何低于 5 分的自动生成描述都必须写明轮次，并以本轮真实文件、函数、接口、日志、报错或数量说明具体不足和实际影响；材料确实没有不足时才评 5 分，不能编造扣分点。生成评分会逐项定档，不会为了省事机械地把五项都评为 5 分。测试中的原始数字数组只保留在内部证据，描述改写为容易理解的业务结果，例如“零费用项保持为零、其余费用按提交顺序分配”。某个维度的生成描述没有通过文字规则时，系统保留开发结果和代码复核结论，只定向重写该维度；连续修正仍不合规时，该轮也不判运行失败，而是在导出列表等待人工修改。执行能力按“项目对象、可观察结果、本轮独有数字或故障恢复”表达；真实出现且与判断直接相关的命令可以作为依据，但不罗列无关命令串。五维公开描述会去除 Markdown 反引号，同时保留其中的文件名、函数名、命令和输入值；“全部通过”和“生产构建成功”属于正常事实描述，不会仅因出现这些文字而被拒绝，结果真实性仍按本轮轨迹和验收材料核对。其他高风险公共片段仍会在生成保存前被拒绝并要求重写。通用环境说明和范围免责话术继续保存在内部验收记录中，不复制进五维描述。

新生成的五维点评必须从项目独有业务对象或真实动作切入，不再以“第 N 轮”“本轮”“本次”作为通用开头；轮次仍在后文明确写出。满分点评若记录本轮首次检查失败、定位或调整后才通过，会按所属维度降低分数，并同步更新该维的 `when`、`behavior`、`impact`、`expected`、`evidenceRefs` 和 `processFindings`；预期输入拦截、历史基线和明确环境故障不因此误扣。

自动生成的描述优先使用“没有、还没、都、有”等口语表达，少用“未、均、包含”，并直接描述业务行为，不使用“用户”这类泛化主语。生成、展示和提交前会把一般的“用户”改成“操作人员”，把“用户界面”改成“页面”；其他措辞整理不会改动代码、文件名、接口字段、原始报错或引号内原文。

人工评分草稿允许先保存，避免编辑内容因文字规则丢失；保存后会立即显示提交前检查结果。导出页发现自动评分存在可由本轮题面、验收结果和轨迹支撑的描述问题时，会按轮次指纹进入独立后台队列，定向重写命中的维度并自动复检；同一版本不会重复调用，临时 504 或网络中断只自动重试一次，修复内容和成功状态在同一事务中落库。落库前若检测到人工修改、资料变化或远端质检已经开始，旧结果会自动废弃。缺少 SessionID、PromptID、轨迹或轨迹摘要等真实材料时不会补造内容，仍保留“待补资料”阻断；已进入远端质检或已有人工评分的轮次也不会被自动覆盖。Excel 导出和 SOLO-QA 提交会与自动生成阶段执行同一套核心规则：非满分描述必须写明轮次，把不足定位到具体步骤、文件、函数、接口或报错，并说明客观后果；满分描述必须有实际核对或验收依据，且不能同时保留错误操作、遗漏、失误或返工等扣分点。句式和措辞仍只作为生成建议，不会因为没有使用固定模板而拦截。

评分生成和提交前检查都会把环境、网络、权限、系统解释器、包管理器和系统运行库问题排除在能力扣分依据之外。提交前只读现有轨迹和验收记录核对负面事实，不修改轨迹文件、摘要或附件：文件、报错和重复调用次数必须能在现有证据中找到；状态清空、内容覆盖和架构不匹配等因果判断必须有直接输出，不能只根据后续结果反推。

评分前还会按后端、前端、页面场景和一次性验收分别提取最后一次带数量的结果。同类检查以后出现的记录覆盖早期记录；如果描述仍把已经恢复的失败写成最终失败、未复验或缺少通过记录，系统只重写对应维度。

## 完成后继续迭代

Bug 候选摘要漏写正确状态时，控制台会从同一条内部 `expected` 证据自动补齐，不再为这类表达问题重新扫描仓库；复现真实性、项目关联和历史重复仍然硬拦截。Feature 与完整模块的候选生成最多 12 分钟，独立复核最多 10 分钟，纯表达格式修复最多 3 分钟；出题阶段优先使用已有项目上下文，只读取确认候选所需的源码，不运行完整测试或构建。

当 0-1 任务和它的全部 Bug 修复通过检查后，进入该任务详情页顶部的“新建独立迭代会话”，可以选择“完整模块构建（0-1 代码生成）”“平滑扩展（Feature 迭代）”或“现有问题整理（Bug 修复）”，再点击生成按钮。系统固定使用 `gpt-5.6-sol` 读取当前干净的 Git 工作树，以及从根任务到当前版本的完整迭代历史：0-1 类型要求在当前项目中从零形成此前不存在、可独立验收的完整纵向模块，Feature 类型要求复用既有核心对象并平滑扩展现有流程。每轮会保存扩展方向、工程核心、用户主流程、修改模块、复杂维度、接口或操作及状态集合，后续出题会同时比较这些结构化信息和完整题面，拒绝只换名称的重复状态、闸门、审批、导出或错误处理。已经失败、停止或中断且没有形成有效产物的迭代仍保留在历史中，但标记为 abandoned，不占六轮配额也不永久阻塞项目链；再次发起时系统重新读取远端 `main`。如果远端已经更新而历史工作区仍停留在旧提交，系统会在内部缓存中检出远端最新提交，历史工作区保持不动，新会话仍从最新代码开始。运行中的迭代仍会阻止重复创建。

Feature 与完整模块使用硬范围预算控制实现负担，但不在题面中写难度标签：题面统一为 300～480 字、四至六个完整句子、分号不超过两个且单句不超过 120 字；只涉及三至四个逻辑模块、一个工程核心、一条用户主流程、最多两个新增接口或用户操作、最多一组新增状态、一项复杂机制和三至四个验收场景。Feature 不得增加独立运行组件；完整模块最多增加一个独立运行组件，且不能与复杂机制同时出现。新的分布式协调、密码学证明、自定义二进制协议、复杂求解器或完整跨进程恢复不能作为迭代核心。生成结果先通过本地结构化硬校验，独立复核再从实际题面重新提取范围，不采信候选自报的数量；少报、合并机制、成功历史实质重复或模板化表达都会被退回。失败题面不被当作已经实现的功能，可以根据当前代码重新设计，但不会原样重发。题面按业务因果自然组织，不机械拼接数据库、接口、页面与测试字段，不连续堆叠命令句，不使用“沿用既有不变量”“其余失败沿用错误信封”等模板短语，也不在结尾集中罗列通用清单。内部范围筛选条件不会写进题面，出题模型与页面选择的开发模型相互独立。

独立 Bug 修复任务会先在最新成功代码上检查并复现问题，选择集中在同一用户流程、预计修改范围为小或中的三至四个真实 Bug。第一轮题面由项目专属范围说明和客户可读的问题摘要组成，只描述业务对象、触发条件、错误表现和正确状态，不给解决方法、技术实现或通用验收清单；无法稳定复现、属于环境故障或已经在成功历史中修好的问题不会进入题面。自动补题的六轮链默认在第 2、5 轮安排 Bug 修复，第 3、6 轮仍可安排完整模块，其余位置使用 Feature。开发完成后的检查若仍发现 Bug，后续修复轮直接按原顺序用中文分号连接问题摘要，不添加固定开场或编号。

Bug 检查的详细复现步骤、实际结果、预期结果和命令证据保存在检查记录中，不再全部塞进发给开发者的题面。每个 Bug 的客户摘要只用一句话说明项目对象、触发条件、当前可观察结果和正确状态，不自行添加标题、序号、引号、实现术语或通用测试清单；系统只负责保持原顺序并连接成无换行题面。同一问题修复后仍存在时，下一轮必须依据新证据描述修复后的残留状态；如果没有新的可观察差异，流程停止自动换词续轮并提示人工确认。

点击后接口立即把出题放入后台，任务状态和当前阶段同时写入 SQLite；页面刷新或控制台重启后会继续识别并恢复，运行中也可点“取消生成”。再次选择同一类型只会等待同一后台任务，已经创建过同类型产出时直接返回原运行记录。Feature、Bug 修复与 0-1 共用每条链最多 6 个有效独立任务的额度；完整模块最多两个且不能连续创建，手动选择和自动补题执行相同配额与全局六槽限制。每次生成题面和创建目录前，系统都会读取 GitHub 远端 `main` 的实际 HEAD；存在同提交的干净工作区时直接使用，否则把该提交克隆到内部只读基线缓存。新记录的 GitHub 初始快照和克隆 commit 始终指向实际远端 HEAD，不会从旧代码分叉，也不会改写历史任务的工作区。单个来源暂时无法准备基线时会进入冷却并跳过，不再立即关闭整个自动补题。生成通过后，系统会立即新建一条运行记录，打开新 Terminal，启动新容器和新 SessionID，再把该最新 Git commit 克隆到新的 `/workspace` 并执行需求；不续接旧对话，也不预先改变来源任务。生成或复核失败时不会创建半成品运行记录，错误会写入来源任务时间线并允许再次点击。任务完成后如果检查出真实且与本轮需求直接相关的 Bug，只在这个新 SessionID 中继续修复和复查；无关历史问题只记录为质量建议，不进入修复题面。
